# OSS protocol-bridge findings for Torana

Pinned 2026-09-14: Bifrost [`cd1b79a`](https://github.com/maximhq/bifrost/tree/cd1b79a6b8df6e3047a316d36e8f6e99421488f4) ([Apache-2.0](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/LICENSE)), CLIProxyAPI [`7fa443d`](https://github.com/router-for-me/CLIProxyAPI/tree/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697) ([MIT](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/LICENSE)), LiteLLM [`9e1ed40`](https://github.com/BerriAI/litellm/tree/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb) ([MIT](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/LICENSE) outside `enterprise/`, which has a separate license). These are design references, not evidence of blanket provider compatibility.

## Reusable patterns

### 1. Give every streamed translation a request-scoped state machine

CLIProxyAPI's Claude-to-Responses state is a useful inventory: one object owns the response ID and timestamp, monotonically allocated output indexes, source-block-to-call/name/ID/index maps, per-call argument buffers and completion flags, ordered message/reasoning items, stop reason, and accumulated usage ([state definition](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/translator/claude/openai/responses/claude_openai-responses_response.go#L17-L59)). Bifrost independently converges on the same shape: content-index to output-index/type, argument buffers, stable item IDs, accumulated output items, stop state, and one-shot lifecycle flags ([Bifrost state](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L63-L88)).

This state is protocol state, not plugin-visible conversation data. Torana's bridge should keep it outside `engine.ChatRequest`/the ABI. Allocate destination indexes in observed source order, preserve one response ID throughout the stream, and correlate later deltas/done events by source item/block identity. Bifrost emits `response.created` then `response.in_progress` exactly once ([conversion](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L869-L943)) and builds terminal `response.output` by walking output indexes in order ([terminal aggregation](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L2776-L2835)).

LiteLLM shows the minimum Responses-to-Anthropic version: item ID to block-index mapping, a monotonically allocated Anthropic block index, and one-shot message start/stop flags ([wrapper state](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L30-L102)). Its E2E suite documents why stable IDs are observable: OpenAI accumulators can discard later chunks when a bridge generates a different ID per chunk ([regression and assertion](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/tests/e2e/llm_translation/test_responses_bridge_streaming_e2e.py#L1-L14), [test](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/tests/e2e/llm_translation/test_responses_bridge_streaming_e2e.py#L98-L121)).

Do not copy permissive recovery blindly. LiteLLM synthesizes a text-block start when an upstream omits `response.output_item.added` ([fallback](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L198-L214)), but its iterator also logs conversion exceptions and then ends without an Anthropic error or `message_stop` ([exception path](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L367-L392)). Torana's existing fail-closed posture is safer: pre-header conversion failures should be a destination-shaped 4xx/5xx; post-header failures should be one destination-shaped stream error followed by transport termination.

### 2. Tool IDs are referential integrity, and result topology is part of the protocol

For ordinary function calls, preserve one identity tuple `{source item/block, call ID, tool name, destination index}` for the whole turn. Start with the destination-required empty object, append argument bytes without parsing partial JSON, and only validate the concatenated document at call end. LiteLLM directly maps `response.output_item.added` to Anthropic `tool_use` with `input:{}`, and maps argument deltas by `item_id` to `input_json_delta` ([tool start](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L152-L178), [argument delta](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L258-L294)). CLIProxyAPI keeps call IDs and output indexes keyed by the source Claude block index ([state](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/translator/claude/openai/responses/claude_openai-responses_response.go#L29-L37)).

Anthropic results are not standalone `role:"tool"` messages. Parallel results must occupy the immediately following user turn, before any trailing user text. Torana already pins both invariants in native adapter tests ([parallel coalescing](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/anthropic/adapter_test.go#L372-L451), [result adjacency](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/anthropic/adapter_test.go#L520-L605)); bridge-level tests must prove them across Responses/Chat/Gemini input shapes. Preserve `is_error` only where representable; Bifrost has a focused test showing that dropping it changes replay behavior ([test](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/toolresultiserror_test.go#L9-L80)).

Do not silently invent correlation for missing, duplicate, or orphan IDs. Bifrost deliberately degrades an orphan Responses output to user text because Anthropic rejects an unmatched `tool_result` ([regression test](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/orphantoolresult_test.go#L11-L17)), but that changes semantics. Torana's explicit bridge should instead reject it as unsupported/malformed unless the product intentionally adopts and documents that fallback. OpenAI Responses parsing currently validates ID/name/input for custom calls but not ordinary `function_call` (`call_id` and `name` can enter the IR empty) ([Torana parser](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/openai/adapter.go#L916-L954)); bridge validation must cover the ordinary case.

Anthropic-compatible targets constrain tool IDs to a smaller vocabulary. CLIProxyAPI replaces invalid characters and generates a fallback for empty IDs ([sanitizer](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/util/claude_tool_id.go#L14-L29)). If Torana supports such normalization, apply one request-scoped forward/reverse map to both call and result; raw replacement alone can collide (`a.b` and `a/b`). Rejecting unrepresentable IDs is a valid, safer first release.

### 3. Translate only the common semantic subset; gate built-ins individually

Provider-native tools are separate protocols, not variants of a function call. Bifrost needs dedicated state for web search, tool search, computer use, MCP, advisor, and code execution ([state inventory](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L51-L61), [ordinary function vs MCP branches](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L1492-L1582)). CLIProxyAPI likewise pairs `server_tool_use` and `web_search_tool_result` by tool ID into one Responses item ([pairing state](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/translator/claude/openai/responses/claude_openai-responses_response.go#L51-L68)). This supports Torana's initial boundary: ordinary function tools only; reject free-form/namespaced/built-in tools, signed reasoning, cache controls, safety settings, provider metadata, and server-tool results unless a destination-specific mapping and test exists.

Bifrost sometimes drops target-unsupported tools but records the dropped types in response metadata ([builder policy](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/requestbuilder.go#L299-L313), [schema field](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/schemas/bifrost.go#L1800-L1804)). Torana should keep returning an explicit `UnsupportedError` for configured translation: silent omission can make a model answer without a required tool.

### 4. Canonical request fields must be consumed; source extensions must not cross protocols

On the pinned Torana tree, Responses parsing excludes only `model`, `input`, `tools`, and `stream`, so `instructions`, `max_output_tokens`, `temperature`, and `top_p` remain source `ProviderExtensions` rather than canonical fields ([parser](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/openai/adapter.go#L1008-L1035)). The same-protocol test explicitly expects `instructions` and `temperature` to remain extensions ([test](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/openai/adapter_test.go#L365-L406)). A bridge must therefore promote these before projection and start destination extensions empty; otherwise Responses-to-Anthropic emits illegal OpenAI members, omits required `max_tokens`, and loses instruction semantics.

Fold all leading Responses `instructions` plus system/developer input items into destination system blocks in source order. Torana's Anthropic marshaller currently serializes only the first system message ([marshaller](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/format/anthropic/adapter.go#L703-L715)), so the bridge must coalesce leading system blocks and reject mid-conversation system instructions for preamble-only targets. CLIProxyAPI implements the same ordering rule: instructions first, then system/developer items, each preserved as a separate block ([request translator](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/translator/claude/openai/responses/claude_openai-responses_request.go#L126-L179)).

### 5. Terminal state and usage need explicit normalization rules

Terminal translation should distinguish success, truncation, refusal, and failure. CLIProxyAPI maps Anthropic `max_tokens` to Responses `response.incomplete` with `incomplete_details.reason="max_output_tokens"`, and everything else to completed ([mapping](https://github.com/router-for-me/CLIProxyAPI/blob/7fa443dc8bf8ca2f1ffd81c2472deb31b097b697/internal/translator/claude/openai/responses/claude_openai-responses_response.go#L154-L173)). LiteLLM recognizes `response.completed`, `response.failed`, and `response.incomplete`, but maps failure to `end_turn` unless refusal/tool state intervenes ([terminal mapping](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/experimental_pass_through/responses_adapters/streaming_iterator.py#L296-L350)); treat that as a bug to avoid. Torana must never turn `response.failed` or a provider stream error into a successful stop.

Choose one canonical token meaning. Both Bifrost and LiteLLM expose OpenAI prompt/input totals inclusive of cache reads and writes, while retaining cache detail separately: Bifrost adds both cache counters to Responses input/total tokens ([Bifrost](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/responses.go#L896-L918)); LiteLLM does the same and derives uncached text tokens by subtraction ([LiteLLM](https://github.com/BerriAI/litellm/blob/9e1ed40db3376dc8e7b9392aa104653ca22d3fdb/litellm/llms/anthropic/chat/transformation.py#L2324-L2414)). Torana's current `StreamUsage.InputTokens` intentionally has provider-dependent meaning ([type comment](https://github.com/torana-edge/torana-edge/blob/a3f891615f802a4ecef3aaaaafb4572d6505bb38/internal/engine/types.go#L220-L234)); a cross-protocol bridge needs a normalization helper or an explicit `uncached_input_tokens` field to avoid under/over-counting during Anthropic/OpenAI conversion.

## Transport boundary: path, auth, and errors

Keep path and credentials out of body adapters. Rewrite the endpoint from the configured destination protocol (`/v1/chat/completions`, `/v1/responses`, `/v1/messages`, Gemini model path/query), then run Torana's existing target-provider credential replacement. Test that a managed target receives only its credential and that caller credentials/query keys cannot survive a cross-provider bridge or failover.

There is one concrete missing target requirement: native Anthropic Messages requests require `anthropic-version` as well as `x-api-key`; Anthropic's own examples send both ([Anthropic Messages tool-use example](https://docs.anthropic.com/ko/docs/agents-and-tools/tool-use/overview)). Torana managed auth installs `X-Api-Key` for an Anthropic-format provider but has no provider-header setting or bridge injection on the pinned tree. An OpenAI/Gemini client will not normally provide `anthropic-version`, so native Anthropic bridge calls can fail before model execution. Inject a documented version for native Anthropic targets or add explicit operator-configured upstream headers; do not forward source protocol beta/version headers across providers.

Map bridge validation failures to the client's error envelope and a non-retryable 4xx before dialing upstream. Once upstream responds, retain HTTP status while translating only known error envelopes. Bifrost's Anthropic error adapter preserves nested type/message and emits a proper `event:error` SSE frame ([error conversion](https://github.com/maximhq/bifrost/blob/cd1b79a6b8df6e3047a316d36e8f6e99421488f4/core/providers/anthropic/errors.go#L11-L72)); Torana should add equivalent destination-envelope tests without reflecting prompts, raw bodies, URLs containing keys, or credentials.

## High-value Torana tests still needed

1. Request matrix for each enabled direction: ordered leading instructions/system blocks, destination token-limit name, temperature/top-p, ordinary tools, two parallel calls/results, empty `{}` arguments, mixed `[tool_result, tool_result, text]`, and no source-only extension keys in the destination JSON.
2. Negative request matrix: empty/duplicate call IDs, orphan/duplicate results, name mismatch, ID characters invalid for Anthropic, mid-conversation system, provider-native tools, reasoning/signatures, cache controls, safety settings, strict schemas, multimodal tool results, and malformed complete argument JSON. Assert deterministic client-shaped 4xx and zero upstream requests.
3. Non-stream response matrix: text plus multiple function calls in wire order, exact IDs and raw argument integers, stop/length/tool status mapping, cache-inclusive totals plus cache details, and explicit refusal of server-tool/reasoning/refusal/image output that the canonical response cannot represent.
4. Stream trace matrix: one stable response/message ID, monotonic indexes, no delta before its start, fragmented/interleaved parallel arguments correlated by item ID, each block/call closed once, terminal emitted once, late/early/missing usage, max-token incomplete, upstream error before headers, error after headers, malformed/truncated SSE, and caller cancellation.
5. Transport E2E: path/query rewriting including provider base-path prefixes, Gemini URL escaping and `alt=sse`, target credential replacement on primary and fallback, required Anthropic version header, target SSE/JSON `Content-Type`, and destination-shaped error bodies/events for 400/401/429/5xx.
